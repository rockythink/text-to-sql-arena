# SQL 模型评测台：题库与裁判有效性审计

审计日期：2026-09-17。范围：冻结 v2 的全部 18 题、当前确定性裁判、接入证据，以及第 18 场的 36 条已保存 SQL。

## 结论

**题库值得保留，但当前总分不足以支持细微的模型能力排名。先修裁判，再明确题意、加强数据，不需要增加 Agent 或自动纠错链路。**

逐题主处置：**7 题保留、5 题加强数据、5 题明确题意/口径、1 题修正参考答案**。保留题目不代表相关通用裁判没有问题；例如第 3、12 题仍受数值归一化或别名检查影响。

已复现：

- 错误计数 `COUNT(...) + 0.4` 得到 **100 分且被判结果正确**。
- 不改变算法与结果，只改表别名或 CTE 名称，分别被扣 **15 分、7.5 分**。
- 一条历史 SQL 因 `generate_series` 被阻断、仅得 5 分；经审阅后在只读隔离副本执行，**12 行与金标全部匹配**。这是安全政策阻断，不是已经证明的业务计算错误。
- 原始数据漏掉了日期端点、金额分层阈值、重复退货、非完成订单支付、无明细对账等关键边界。
- 参考 SQL 能复现自身金标，不等于独立证明参考答案正确。第 4 题已有舍入改变筛选结果的确定反例。

**本次仅审计：没有修改应用代码、评分器、发布题库或历史分数；没有调用待测模型、执行健康检查或付费评测，也没有提交、推送或部署。**

### 必须区分的两类结果

60 个定向变异中，50 个被结果比较拒绝、10 个在原始数据上结果相等；其中 9 个总分 100：

- 第 6 题 RANK 在原数据结果相等，但违反题面明示的 ROW_NUMBER，得 85 分。**这是合法语法约束扣分，不是别名误判。**
- 第 10 题省略 completed 过滤是支付口径歧义，不能因为与参考在变体上不同，就直接称其业务错误。
- 其余 8 个满分变异涉及日期包含端点、均值等号、退货放大、两个金额分层错误、支付状态过滤和两个对账遗漏；定向变体暴露了问题。

这是刻意选择的反例样本，不能据此估计一般 SQL 错误漏检概率，也不能称为穷尽验证。

## 裁判问题与优先级

### P0：数值归一化先舍入，错误计数被判相等

证据 J01：第 3 题把 `COUNT(o.order_id)` 改成 `COUNT(o.order_id) + 0.4`，120 行均通过，得 100 分。J02 将偏差改为 0.6 后被拒绝。

根因在 `backend/app/services/result_compare.py` 的 `_number_cell` / `normalize_cell`：题级 `decimal_scale` 应用于所有数值单元格，在容差比较之前先量化。该题 scale=0、绝对容差=0，并未因此获得精确整数比较。

建议：计数与 ID 按精确数值合同比较；货币、比例按列定义精度及容差；展示舍入不要改变判等。`12.0` 与 `12` 可以数值等价，但 `12.4` 不等价。修复使用新 scorer 版本，不能覆盖旧分。

### P1：AST 对无关命名敏感，同时没有真正验证全部防放大要求

- J04：第 12 题仅将表别名 `p` 改为 `payment_source`，结果相同、ROW_NUMBER 分区与排序算法相同，仍由 100 变 85。
- J05：第 11 题仅将 `sold`、`returned` 改为 `sales_totals`、`returns_totals`，由 100 变 92.5。
- Q11：保留原 CTE 名称，但在 sold 内部加入会放大销量的退货明细连接，原数据仍得 100。第二条退货使品类-6 sold_qty 从正确 667 放大成 669。

根因涉及 `sql_evaluator.py` 的 `_canonical_expression`、`_window_matches`、`_separate_preaggregation`。结构检查不能等同于参考 SQL 命名检查，也不能靠检查存在某些 CTE 就证明防放大。

建议：业务结果仍主导，明示语法约束另列；必要结构检查基于作用域、列来源和聚合关系。优先用具有真实一对多关系的数据检验防放大，不增加 LLM 裁判。

### P1：安全政策阻断被混入 SQL 能力结论

J06：`run-0018/case-run-00153.json` 使用 `generate_series`，被生产 guard 的 FROM 表函数禁令拒绝。原 SQL 经审阅后在临时只读 DuckDB、关闭外部访问的环境直接执行，列名、行数、顺序和 12 行数据均匹配原金标。

这只证明该 SQL 在该冻结数据上的结果；不证明它对全部缺月或其他业务口径也正确，**更不产生新官方分或新赢家**。

J07–J09 同时确认：纯内存 generate_series、文件读取 read_csv、DELETE 均被现有 guard 拦截。不得据此删除安全防线。

可选路线：

1. 保持禁令，但在生成 Prompt 明示“禁止所有 FROM 表函数”，并把政策阻断与已执行结果错误分开。
2. 经安全审查后仅放行有界、纯内存表函数白名单；保留文件/网络/写入禁止及执行资源限制。

这里是需要确定的公开评测合同，不是给个别历史模型特判。

### 列顺序：已文档化的合同选择，不冒充新 bug

J03：同名列换顺序，行数据相等，得 95 分且 `result_correct=false`。现有 `docs/methodology.md` 明确要求归一化列名及原顺序一致；实现符合该约定。

若主指标想表达“业务结果正确”，应另列数值/行集合正确与输出格式合同通过率。当前 result_correct 包含列顺序，不能无说明地当作与格式无关的业务正确率。

J10–J16 检查的重复行、要求排序、不要求排序、容差边界、NULL 与 0、空结果边界均符合各自设定。

## 接入路径与无辅助边界

当前应用没有框架级 Agent 编排或 SQL 自动修复循环。`benchmark_engine._run_case` 构造请求后调用一次 adapter.generate，再执行确定性评估；生成请求不包含 reference SQL、金标和内部 AST 规则。

但 **应用没有 Agent 循环，不等于 CLI 没有自身 harness 行为**。

第 18 场双方均记录：Codex CLI 0.147.0、同样的隔离控制、文本返回、timeout=180 秒、单次尝试。这支持“相同已记录 CLI 条件下比较”，不等于裸 HTTP 模型能力比较。

- Codex 运行使用临时目录、忽略用户配置和规则、只读沙箱及项目目录隔离。不能把这直接表述为“已证明完全不使用任何工具”。
- J18 仅用合成 JSONL 测试 parser：带 command_execution 事件时，解析器仍接受后续回答，不拒绝该事件，提取出的回答也不保留工具事件。没有实际执行该合成命令，也没有调用 Codex。
- J17：没有服务端 model 字段时，parser 用请求名填 resolved_model_id。因此该字段未必是独立确认的身份；本次没有证据断言历史两次调用实际走过该回退。
- Gemini parser 显式拒绝工具事件；Claude CLI 带禁工具参数。不同 CLI 的控制机制不能不加披露地视作同一个条件。

建议：主榜优先使用直接 API、单次提示、不给工具、不回传 SQL 错误、不重试修复；CLI 单列接入条件。记录模型身份来源（服务端报告/请求值回退）及经脱敏的工具事件摘要。不能声称历史实际用了工具，也不能仅凭当前存证声称绝对无辅助。

历史第 18 场按当前结果合同复放，双方仍为 16/18；原综合分 95.09 与 92.04 保留。不能把该分差直接解释为同等大小的业务正确能力差距。

## 后续实施顺序（本次未实施）

1. 修数值判等与别名敏感检查，明确业务结果、语法约束、输出格式、安全阻断各自指标。为已确认 bug 保留最小反例回归。
2. 先确定第 4、6、7、8、10、17 题口径，再改参考与 Prompt；不要先按错误参考批量造金标。
3. 增加日期端点、均值精度、并列商品、空月/零月、重复退货、金额分层端点、pending 支付、无销量品类、无明细/非完成订单异常等确定性数据。
4. 构建新的冻结题库版本及评分版本。用本报告的独立 SQL、变异和边界增量验证后再发布，保留旧 v2 与历史报告。
5. 新合同稳定后才安排模型重测；主指标用明确界定的结果正确率，原综合分保留为辅助分解。不得从本次审计旁路执行推算“修正后的官方赢家”。

目标是让测试准确地区分 SQL，而不是让更多 Agent 帮模型把 SQL 做对。
